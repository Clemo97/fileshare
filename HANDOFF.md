## 0. Read this first

**What this is.** A peer-to-peer file sharing product. The original is a Next.js web app (`file-share-rtc/`) that moves files directly between browsers over WebRTC, with Supabase for sign-in, pairing and signaling. This work builds an iOS and Android app for it with Expo and React Native (`apps/mobile/`), reusing the same backend and the same wire protocol.

**Where it stands, in one paragraph.** The mobile app's screens are finished. **Real pairing through Supabase works**: a hosted free-plan project exists, the pairing code was tested against it (33 live checks) and was driven end to end through the app's actual UI on two iOS simulators, where each device generated or entered a code and then listed the other as a connection. A WebRTC spike proved that a phone can exchange files with a browser using the web app's protocol. **Real file transfer is built** (picker, request and accept dialog, signaling through Supabase, one WebRTC data channel per file, saving on the receiver) and was verified between two simulators with byte-identical files. **The owner then reported it working on the physical iPad and S23 (re-pairing, sending a file and saving it)** with only public STUN servers, so a TURN relay was **not** needed in that test. How big the file was, how fast it went and whether both devices were on the same Wi-Fi were not recorded (§3.6, §10).

**The Supabase setup was done on 2026-11-02.** The owner authorized it using a personal access token kept in 1Password, paused it once to ask for this document, then told it to continue. Free-plan projects are paused after a period of inactivity (about a week, **[from memory; check current rules]**): if the app ever shows "Couldn't sign in", check whether the project is paused in the dashboard.

## 3. Architecture and the reasons for each choice

### 3.1 Stack

Expo SDK 58 (`~58.0.22`), React Native 0.88.1 (New Architecture only), React 19.3.0, TypeScript ~6.0.3, Expo Router (file-based routes in `src/app/`), `react-native-webrtc` ^155.0.1 with `@config-plugins/react-native-webrtc`, `@supabase/supabase-js` ^2.118.0, AsyncStorage 2.2.0, Reanimated 4.7.1. React Compiler is on (`experiments.reactCompiler`). `web.output` is `"server"` (the Expo template default, and the source of trouble in G2).

**Why Expo/React Native** (plan §3): the web app is already React + TypeScript and about 2,600 lines of its core logic (XState machines) have almost no DOM code, so it can be reused. Native (Swift + Kotlin) means two codebases and no reuse; Capacitor is kept as a fallback only. **Why a development build, not Expo Go:** `react-native-webrtc` has native code.

### 3.2 Planned architecture (not fully built)

A shared TypeScript core (`packages/core`) used by web and mobile, receiving platform pieces through XState `input`: a `FileSource` for sending, a `FileSink` for receiving, and a `createPeerConnection()`. Plan §5 has the interfaces. Today this core **does not exist**; the mobile app uses a stand-in "demo store".

### 3.3 Demo mode versus live mode (a deliberate design)

The app was built "UI first": screens run on `src/features/demo-store.tsx` (a reducer plus timers) and `sample-data.ts` so they could be reviewed before any networking existed. That mode is kept on purpose:

- If `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_ANON_KEY` are **absent**, `src/lib/supabase.ts` exports `null` and everything behaves exactly as the old preview (`session.status === 'demo'`).
- If they are present, the app signs in anonymously, loads the user's profile and uses real pairing, a real connections list and **real file transfer** (§3.6). In demo mode transfers are still simulated.
- The client is also `null` when `Platform.OS === 'web'`. This matters: the release build pre-renders routes on Node, and evaluating Supabase or native-only code there must not crash (G2). Verified with `npx expo export --platform web` using fake env values.

### 3.4 Pairing: how it works now

Web app (unchanged): code creation and redemption run in Next.js server actions using the **service-role key**, then a WebRTC handshake, then the code creator writes `user_connections`.

Mobile cannot hold the service-role key, so the same two steps became database functions in `20261102120000_pairing-functions.sql`:

- `create_pairing_code() returns jsonb` gives `{"code": "1234", "created_at": ...}`. 4 digits from `gen_random_uuid()` (a CSPRNG), replaces the caller's previous code, frees expired codes, retries on collision, fails with `no_code_available` if all 10,000 are taken.
- `redeem_pairing_code(p_code text) returns uuid` gives the code creator's user id, or **null** if the code is wrong, expired (5 minutes), already used, or the caller's own. Per user, at most 5 failed attempts in 10 minutes, then it raises `too_many_attempts`. It returns null (not an exception) on a wrong code because an exception would roll back the attempt record.
- Both are `security definer`, require `auth.uid()`, and are executable only by `authenticated` (anonymous sign-ins use that role).
- `pairing_attempts` is a new table with RLS enabled and no policies, reachable only through the function.

**Deliberate deviation from the web flow:** `redeem_pairing_code` also inserts the `user_connections` row (code creator as `user_1_id`, redeemer as `user_2_id`), instead of waiting for a WebRTC handshake. Reason: this slice has no WebRTC, and doing it atomically means both devices see the connection even if the creator's app is in the background. Consequence: **the web app and the new functions are two parallel pairing mechanisms.** If a web user redeems a mobile user's code through the web flow, the web side waits for a handshake that never comes. Mobile-to-mobile only, for now. When WebRTC is wired in, decide whether the connection row should go back to being created after a successful handshake.

Client flow (`apps/mobile/src/app/connect.tsx`, `src/features/pairing.ts`):

1. Device A taps "Generate Connection Code" and calls `create_pairing_code` through `client.rpc`. The sheet shows the code and a 5-minute countdown.
2. While the code is showing, A listens for an INSERT on `pairing_code_redemptions` (Realtime, filter `pairing_code=eq.<code>`) **and** polls `hasRedemption` every 3 seconds as a fallback. When it fires, A refetches connections and shows "Connection successful".
3. Device B types the code and calls `redeem_pairing_code`. Null gives "That code is wrong or has expired…", `too_many_attempts` gives a friendly message, a network error gives a network message (`describeError` in `src/lib/supabase.ts`). Success refetches connections and shows success.
4. `ConnectionsSync` (`src/features/connections-sync.tsx`) keeps the list current: it fetches on sign-in, refetches on any `user_connections` Realtime event and whenever the app returns to the foreground (Realtime can miss events while suspended), and feeds the store through `syncConnections`, which keeps any in-progress transfer (real or simulated) for people who are still connected.
5. Deleting a connection calls `deleteConnection` when live, else only the local store.

### 3.5 Why releases are used on the physical devices

The owner's Wi-Fi blocks device-to-device traffic (evidence in G1). A debug build fetches its JavaScript from Metro on the Mac over Wi-Fi, which fails there. Release builds embed the JavaScript, so they work anywhere. This also holds for real pairing: it only needs internet access to Supabase.

### 3.6 Real file transfer: how it works

**Why the owner once saw imaginary files:** the screens were built first on a simulation (`demo-store.tsx`), and when pairing became real the simulation kept running next to it (evidence in §10). Live mode now uses the real engine below; the simulation runs only in the offline demo.

**Flow (sender "S", receiver "R"; all code in `apps/mobile/src/transfer/` plus `src/features/transfer-provider.tsx`):**

1. S taps Send Files. `pickFiles()` (`files.ts`, `expo-file-system`'s `File.pickFileAsync`, multiple files) returns the chosen files. Then `runSend` in the provider runs.
2. S inserts a `file_sharing_request` row (payload `{files:[{name,size,mimeType}]}`, `requests.ts`) and waits up to 2 minutes for a `file_sharing_request_response` row (Realtime plus a 2 s poll).
3. R's `listenForRequests` (Realtime plus a 4 s poll plus a check when the app returns to the foreground; only unanswered requests from the last 10 minutes) puts the request in the store, which shows the existing dialog. **Accept** calls `receiveFiles`, waits until R's side is listening (`ready`), and only then writes the response row. **Cancel** writes `accepted:false`; S shows "They declined the transfer." on the card.
4. S is the WebRTC caller (`session.ts`): it creates one data channel per file (`file:<index>`, like the web app), makes the offer and sends it through `web_rtc_signals`; R answers. ICE candidates travel the same way. `signaling.ts` listens through Realtime (filter on the remote user) **and** polls every 1.5 s, de-duplicating by row id; signals are applied one at a time in arrival order. Both sides delete their own signal rows when done.
5. Each file then runs protocol v2 (`protocol.ts`, from plan §6.1): R sends `{ready:true}`; S waits up to 3 s, sends the metadata JSON and 50 KB chunks, at most 64 unacknowledged; R acks every 16 chunks, writes every chunk **synchronously** inside the message handler, and sends `{done:true}` when it has every byte. Files go one after another over their own channels.
6. R saves each file under the app's cache folder (`received/<random id>/<safe name>`). The file row shows a **Save** button that opens the share sheet (`expo-sharing`) so the user can put it in Files, Photos and so on. The screen is kept awake during a transfer (`expo-keep-awake`, loaded lazily).

**State** lives in the store (`demo-store.tsx`): the engine drives it through `store.engine` (`begin`, `progress`, `fileDone`, `setStatus`, `fail`, `setRequest`). Progress never moves backwards and is throttled to about 5 updates a second. A failure sets `connection.error` and returns the card to idle, where the card shows the message in red.

**ICE servers** (`ice.ts`): public STUN (Cloudflare, Google), plus anything in the `EXPO_PUBLIC_ICE_SERVERS` env var (a JSON array of `RTCIceServer`), plus whatever a Supabase Edge Function named `turn-credentials` returns (**the function does not exist yet**; a missing function is remembered for 10 minutes so each transfer does not wait for it).

**Native-module rule:** `react-native-webrtc`, `expo-file-system`, `expo-sharing` and `expo-keep-awake` are all loaded with a lazy `require` inside functions, never at module scope, so the Node pre-render of the release build (G2) never touches them. Keep it that way.

**Dev shortcut:** `mobile://home?sendTest=3,12&n=1` generates files of those sizes in MB (byte at position `p` is `(p*131+17) & 255`, so a receiver can check them byte for byte) and sends them to the first connection without opening the picker. Change `n` to send again. Works only when `__DEV__`.

**Limits and choices to know:** the whole file is never held in memory (the sender reads 50 KB at a time, the receiver writes as it goes); a transfer needs both apps open (nothing is delivered in the background); if the sender's app dies mid-transfer the receiver keeps whatever files finished and drops the unfinished one; a request that is never answered times out after 2 minutes; the connection step times out after 30 s with a message that mentions a relay server.

**TURN (not needed so far, still wanted):** the iPad and S23 connected and transferred with **public STUN only**, on the owner's network, which §6.2 had guessed would block it. Do not read that as "TURN is never needed": it says nothing about cellular data, guest or office Wi-Fi, or two different networks, and it is not known whether both phones were on the same Wi-Fi. When a link cannot form, the card shows a message saying a relay server is needed (30 s timeout). A TURN relay needs an account with a provider (plan §2.1 names Cloudflare Realtime TURN, which has a free tier; Metered is an alternative) and short-lived credentials minted by an Edge Function. **The owner has to create the account.** For a quick test before the Edge Function exists, put the provider's credentials in `EXPO_PUBLIC_ICE_SERVERS` in `.env.local` and rebuild (it is inlined into the bundle, so it is not secret; use short-lived credentials or accept that).

Always `export LANG=en_US.UTF-8` first (CocoaPods crashes on a non-UTF-8 locale). Never set `CI=1` for `expo start` or `run` (it disables file watching and serves a stale bundle).

```bash
# Checks required by AGENTS.md before declaring work done
cd apps/mobile && npx tsc --noEmit && npx expo lint

# SQL tests
cd file-share-rtc/supabase/tests && npm install && npm test

# iOS simulator (Debug, starts Metro). Add --no-bundler if Metro is already running.
cd apps/mobile && npx expo run:ios --device "iPhone 18 Pro"

# Physical iPad (Release, JS embedded, exits when done). Get the UDID from `xcrun devicectl list devices`.
cd apps/mobile && npx expo run:ios --device <UDID> --configuration Release --no-bundler

# Android release APK, arm64 only (about 56 MB). R8 is off for now (G3).
export JAVA_HOME=/opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk/Contents/Home ANDROID_HOME=$HOME/Library/Android/sdk
export PATH="$JAVA_HOME/bin:$ANDROID_HOME/platform-tools:/opt/homebrew/bin:$PATH"
cd apps/mobile/android && ./gradlew assembleRelease -PreactNativeArchitectures=arm64-v8a -Pandroid.enableMinifyInReleaseBuilds=false
# APK: apps/mobile/android/app/build/outputs/apk/release/app-release.apk
~/Library/Android/sdk/platform-tools/adb install -r <that apk>
```

Two more checks that were useful:

```bash
# Does the Node pre-render of the Release build still work? (env values can be fake)
EXPO_PUBLIC_SUPABASE_URL=https://example.supabase.co EXPO_PUBLIC_SUPABASE_ANON_KEY=x CI=1 npx expo export --platform web --output-dir <somewhere outside the repo>
# Were the env values inlined into the native bundle? Export iOS and search the .hbc for the URL.
```

The Android phone: Developer options on, USB debugging on, a data cable (not charge-only), USB mode "File transfer", tap Allow on the "Allow USB debugging?" prompt. On Samsung, Auto Blocker can block installs and USB commands.

## 8. Gotchas (symptom, cause, fix). Read before building anything.

**G1. iPad shows a red "No script URL provided" screen.** A debug build loads JS from Metro at the Mac's IP over Wi-Fi; the connection was refused (§6.2). **Fix:** use Release builds on physical iOS devices here. (On Android, `adb reverse tcp:8081 tcp:8081` forwards Metro over USB, so debug builds work there.)

**G2. Release build dies at "Exporting server" with `requireNativeComponent is not a function`.** `app.json` has `web.output: "server"`, so a Release build also pre-renders routes on Node, evaluating the module graph with `platform=web`. `react-native-webrtc` crashes there. `_layout.tsx` imported the spike runner (which imports WebRTC) at module scope. **Fix (commit `32a08cd`):** load it with `require()` inside the dev-only branch. **Rule:** never import `react-native-webrtc` or other native-only code at module scope in anything reachable from a route; use a lazy `require` or a `Platform.OS` guard (as `src/lib/supabase.ts` does).

**G3. Android release fails in R8: `Missing class org.webrtc.Dav1dDecoder$Natives`.** The generated project has `android.enableMinifyInReleaseBuilds=true`. Suppressing the warning alone is unsafe because WebRTC's JNI code calls Java classes by name and R8 can rename them (runtime crash). **Current workaround:** build with `-Pandroid.enableMinifyInReleaseBuilds=false` (bigger APK, nothing in the repo changes). **Proper fix before a store build:** keep rules for `org.webrtc` through a config plugin (for example `expo-build-properties` with `android.extraProguardRules`). Its option names for SDK 58 were **not checked**.

**G4. Gradle: `A problem occurred starting process 'command node'`.** A stale Gradle daemon (from earlier Android setup) had a `PATH` without Node. **Fix:** `./gradlew --stop`, rebuild with `/opt/homebrew/bin` in `PATH`.

**G5. `expo prebuild` wipes `ios/`, including your signing team and the Pods.** Even without `--clean`, SDK 58 printed "Clearing ios". The owner's Apple signing team (an Xcode setting) vanished and had to be restored in the generated `ios/mobile.xcodeproj/project.pbxproj` (`DEVELOPMENT_TEAM`, in both Debug and Release). **Options:** set `ios.appleTeamId` in `app.json` (persistent, but it commits a personal team ID: ask the owner; **[unverified]** that this field exists in SDK 58) or re-add it after every prebuild. `android/` was **not** regenerated after the orientation change, so its manifest still says `screenOrientation="portrait"`; regenerating will let phones rotate (`orientation: "default"` means no lock), and the layouts have not been checked in landscape.

**G6. Debug build fails to link (`Sealable::Sealable()` undefined), then crashes at launch (dyld "Symbol not found: ...CDPDebugAPI::addConsoleMessage", then `SIGBUS` in `ExpoModulesCore` inside React `Props`).** React Native's prebuilt core, the Hermes engine and the dependencies bundle each come in **Debug and Release flavors**; Expo's own prebuilt frameworks (`ExpoModulesCore`, `ExpoImage`, `ExpoFont`, `ExpoFileSystem` and others) have the same switching. Build scripts swap flavors and remember the last one in `Pods/<name>/.last_build_configuration`. A `pod install` between a Release and a Debug build **deletes the markers but leaves the Release binaries**, and the scripts then assume Debug is already installed. A Release-flavored framework cannot satisfy Debug code (debug-only symbols, different struct layout). **Fix that worked:**

```bash
cd apps/mobile/ios && LANG=en_US.UTF-8 rm -rf Pods Podfile.lock && pod install
rm -rf ~/Library/Developer/Xcode/DerivedData/mobile-*/Build/Products/Debug-iphonesimulator/XCFrameworkIntermediates
# then rebuild
```

A targeted repair (write `Release` into the marker, then run React Native's own `replace-rncore-version.js`, `replace_hermes_version.js`, `replace_dependencies_version.js` with `-c Debug`) fixed React core, Hermes and dependencies, but the app still crashed because Expo's frameworks were also the wrong flavor, so only the full reinstall is confirmed to work. The causal chain is mostly inferred from file hashes and logs. Avoid it by not running `pod install` between flavor switches, or expect to do the reinstall.

**G7. iPhone 18 Pro simulator: `Library not loaded: /usr/lib/libSystem.B.dylib` ... "no dyld cache", for our app only.** The same build ran on the iPhone 17 simulator and Safari ran on the 18 Pro, so it was device state. **Fix:** `xcrun simctl shutdown <udid> && xcrun simctl boot <udid>`. Cause unknown. After a reboot the simulator input tool says "input connection is still starting up": wait about 10 seconds.

**G8. Two DerivedData folders** exist for this app (`mobile-evwlqvf...` and `mobile-dcdzdbm...`). Builds use the first. Harmless; do not delete the one in use mid-build.

**G9. `expo run:ios ... --no-bundler`** makes the command exit when the build and install finish, which is convenient for background runs. Without it Metro stays attached and the command never exits. `run` installs but does not always launch: use `xcrun simctl launch <udid> com.anonymous.mobile`.

**G10. Android phone needs a data cable and debugging approval** (§7). `adb devices` lists nothing when the cable is charge-only.

**G11. zsh:** use `${pipestatus[1]}` not `${PIPESTATUS[0]}`; `grep -c` on binary files printed nothing here, so search bundles with Python.

**G12. Fetching docs.** Apple's docs are JavaScript-rendered: fetch `https://developer.apple.com/tutorials/data/documentation/<path>.json` instead. X/Twitter blocks plain fetches (HTTP 402): use a browser pane.

**G13. Xcode skills and the "generated ios/" rule conflict.** AGENTS.md says never hand-edit `ios/` or `android/`. Exceptions made with the owner's knowledge: re-adding the signing team and repairing Pods flavor markers. Both are inside generated, gitignored folders.

**G14. 1Password CLI.** `op whoami` errors ("couldn't connect to the 1Password desktop app") but `op vault list` and `op read` work. Once, `op read` returned an **empty** value, and the next API call got HTTP 401 `Format is Authorization: Bearer [token]`. Always check the value's length (not the value) before using it.

**G15. `npm audit` reports 26 moderate vulnerabilities** in `apps/mobile` after installing the Supabase packages. Not investigated.

**G16. Writing `.env.local` while debug apps are running makes them sign in.** A running Metro hands the new values to already-running debug apps, which then create real anonymous users in the project by themselves. This happened: both simulator apps signed in one minute after the file was written. It is also proof the app's sign-in works. Expect these extra accounts, or stop the apps first.

**G17. Deleting an account leaves its profile behind.** In the original schema `public.users` has no foreign key to `auth.users`, so `delete from auth.users` leaves an orphan `public.users` row (with its pairing codes, attempts and so on). Delete the id from **both** tables; deleting from `public.users` cascades to the dependent rows.

**G18. Migrations were applied through the Management API's SQL endpoint, not the CLI.** That needs no database password. To keep `supabase db push` consistent later, `provision.py` writes `supabase_migrations.schema_migrations` itself, mirroring what the CLI stores (version, name, empty statements). **[unverified]** against a real `db push`. The CLI itself needs the database password, which was random and not kept: reset it in the dashboard (Project Settings, Database).

**G21. A debug app on the simulator may not repaint after a JavaScript edit.** Metro logged the changed module as bundled, yet the screen kept showing the old card (and a harmless LogBox toast, "Sending `onAnimatedValueUpdate` with no listeners registered", which predates the change). `xcrun simctl terminate <udid> com.anonymous.mobile` then `launch` loaded the fresh bundle.

**G22. `npx expo install expo-sharing` edits `app.json`.** It adds the package's config plugin with the "receive shared files" settings. This app only *sends* to the share sheet, so the plugin entry was removed again; check `git diff apps/mobile/app.json` after installing any Expo module.

**G23. `npx expo run:ios` from inside `ios/` fails** with "expected package.json path .../ios/package.json". Run it from `apps/mobile`.

**G24. Opening a deep link on a simulator asks "Open in mobile?" once per device.** Tap Open. The dev shortcut `mobile://home?sendTest=...` needs a connection to exist and a changed `n` value to send again.

**G25. The S23 "is plugged in" but `adb devices` is empty.** Check what the Mac sees: `system_profiler SPUSBHostDataType | grep -i -A3 samsung` (the iPad appears there as "iPad"). If the phone is absent there too, it is a cable that carries only power, a hub, or the phone's USB mode (pull down the notification shade, tap the USB notification, choose File transfer); USB debugging settings and `adb kill-server` do not help. When it works the phone shows as `SAMSUNG_Android` and `adb devices` lists it as `device` after the Allow prompt.

**G20. A naive search for `sb_secret_` in a built bundle gives a false positive.** `supabase-js` has `key.startsWith("sb_secret_")` in its own code, so every bundle that includes it contains that literal. Judge a hit by the library source (`grep` the package), by the shape of what follows, and by what your own `.env.local` holds (here: a publishable key only). Never go looking for the real secret key to compare: it must not be read out.

**G19. The simulator tool redraws late.** After typing or tapping, screenshots can show the old screen for several seconds ("Typed 4 characters" with an empty field was just lag). Wait three to five seconds before judging a screen.

## 9. Supabase: what exists and how it was set up

### 9.1 State on 2026-11-02

- **Project:** name `data-loom`, **free plan**, region `eu-central-1` (Frankfurt), in the owner's single organization ("Personal Projects", on the free plan). Created by `file-share-rtc/supabase/tools/provision.py`. The project ref, URL and organization slug are not recorded here because this repository is public; the URL is in `apps/mobile/.env.local`.
- **Region choice:** Supabase's own recommendation was `us-east-2` (Americas), which looked wrong for the owner's location. Round-trip time from the owner's Mac to each offered region was measured instead: Singapore 141 ms, Frankfurt 152, Mumbai 162, London 184, Ireland 192, Sao Paulo 356, `us-east-2` 295, and so on. Singapore versus Frankfurt was a statistical tie, so Frankfurt was taken as a good all-round choice. The region cannot be changed; to move it, run `provision.py` with another `SB_REGION` (there is no data worth keeping yet) and delete the old project.
- **Anonymous sign-ins:** on. `rate_limit_anonymous_users` is 30 (per hour per IP).
- **Schema:** all five migrations applied (10 tables in `public`, all with row-level security; 6 functions including `create_pairing_code` and `redeem_pairing_code`; the Realtime publication covers `file_sharing_request`, `file_sharing_request_response`, `pairing_code_redemptions`, `user_connections`, `web_rtc_signals`). `anon` cannot execute `create_pairing_code`; `authenticated` can.
- **Keys:** the project has legacy `anon` and `service_role` keys and the new `publishable` and `secret` keys. The app uses the **publishable** key, which works for sign-in, RPC, Realtime and RLS (verified). `apps/mobile/.env.local` (gitignored, mode 600) holds the URL and that key. The service-role and secret keys were never read out.
- **Database password:** random, used once at creation, not stored anywhere.
- **Data in the project right now:** at least four app accounts: the two simulators ("Blue Snail", "Blue Bear", paired by the UI test) and the physical devices' accounts. The devices were reinstalled on 2026-11-02 and probably have **new** accounts now; the earlier "Blue Squirrel" and "Violet Dog" rows and their connection are probably orphaned (the owner can leave them; they cost nothing). **This was not re-queried after the real-transfer tests**, so counts of accounts, connections and transfer-table rows are unknown; the transfer tables are cleaned up by the app after each transfer (requests are deleted by the sender, signals by both sides).

### 9.2 Rules for the token and keys

- The owner keeps a Supabase **personal access token** in their 1Password (an item of category API Credential whose notes say "supabase personal access token"; the token is its concealed `credential` field). **The vault and item names are deliberately not written here because this repository is public: ask the owner.** Reference form: `op://<vault>/<item>/credential`. The token worked (HTTP 200 on `GET /v1/organizations` and `/v1/projects`).
- It is **full account access** (it can delete projects). Use it only for what the owner authorized. Read it inline and never echo it: `SUPABASE_ACCESS_TOKEN="$(op read 'op://<vault>/<item>/credential')" <command>`, with a retry loop and a length check, because `op read` sometimes returns empty (G14). Never pass it on a command line where `ps` can see it. Never write it to a file.
- Do **not** use any other Supabase token you may find on the machine. If you notice a token stored in plain text anywhere, tell the owner. The owner may want to rotate this token now that setup is done, and to expire any 1Password share link that was pasted into a chat.
- The mobile app gets only the project URL and the **publishable/anon** key (public by design). **Never** put the service-role or secret key in the app, the repo, `.env.local` or logs: the api-keys endpoint returns them in the same response as the public key, so extract only the public one (`provision.py` does).

### 9.3 How it was done, and how to redo it

1. Read the account (read-only): organizations, projects, and `GET /v1/projects/available-regions`. The endpoint shapes below were **checked against Supabase's OpenAPI spec** (`https://api.supabase.com/api/v1-json`) before use: `POST /v1/projects` (needs `name`, `organization_slug`, `db_pass`; `plan` and `region` optional, and `plan: "free"` was set explicitly so it can never default to paid), `GET /v1/projects/{ref}` (status becomes `ACTIVE_HEALTHY`), `PATCH /v1/projects/{ref}/config/auth` (`external_anonymous_users_enabled`), `POST /v1/projects/{ref}/database/query` (`{query}`), `GET /v1/projects/{ref}/api-keys`.
2. Run `provision.py` (`SUPABASE_ACCESS_TOKEN`, `SB_ORG_SLUG`, `SB_REGION` in the environment). It creates the project (or reuses one with the same name), waits for health, enables anonymous sign-ins, applies the migrations, verifies what exists, and writes `.env.local`. The project became healthy immediately.
3. Run `e2e-live-pairing.mjs` and clean up the throwaway users (G17).
4. Rebuild the devices so the values are inlined into the bundle (§7). Mind G6.

### 9.4 Still unverified

- Kill-and-reopen keeping the same identity **on the physical devices** (it was verified on the iPhone 18 Pro simulator, and a plain restart was not tried on the phones after the reinstall; the apps having vanished from both is unexplained: after a full restart the app was still "Blue Snail" with "Blue Bear" connected); a real `supabase db push` after the hand-written migration history (G18); behavior after the free project is paused.

## 11. Known unknowns and risks

1. **Live behavior is proven on simulators and by script, and the owner reports the full flow working on the physical devices** (pairing, sending, saving). Realtime delivery worked in every run (redemption and `user_connections` inserts on both sides, and a DELETE event), and the app also polls and refetches on foreground as a fallback. Not yet seen: Realtime across a flaky mobile network, and a long-lived session after the app has been suspended.
2. **4-digit codes and free anonymous sign-ins** mean the attempt limit is not a real brute-force defence (an attacker can create accounts). Longer codes or a global limit are follow-ups (plan §2.3).
3. **Two pairing mechanisms** (web server actions vs the new functions) and different moments for creating `user_connections` (§3.4).
4. **No TURN relay.** The iPad and S23 connected without one on the owner's network, but networks that block direct links (cellular, guest Wi-Fi, some offices) will fail with the "relay server" message until a relay exists (§3.6). Plan: Cloudflare STUN is free; Cloudflare TURN has a free tier, pricing undated in the plan.
5. **Throughput** is bounded by the JS thread (base64 per chunk): about 10 MB/s on the iOS simulator, about 2.5 MB/s on the Android emulator via TURN. Real phones: the owner's test worked but speed was not measured.
6. **Backgrounding** suspends transfers and Realtime on iOS; v1 design is "keep the app open".
7. **Bundle ID is a placeholder** (`com.anonymous.mobile`); it cannot be changed once an app exists in a store. Pick a real one before the first upload.
8. **Camera, microphone and Bluetooth permissions** are added to the manifests by the WebRTC config plugin although a data-only app does not need them (plan §6.1 "Smaller things").
9. **Android R8 is off** in the release APK (G3).
10. **Android rotation** will unlock when `android/` is regenerated; landscape layouts unchecked.
11. **Builds on the physical devices** (§2.3): both run the Supabase-enabled Release builds with real transfer. An app that goes missing from a device (it happened to both on 2026-11-02, cause unknown) loses its anonymous identity and its connections; there is no account recovery. If a device ever shows sample data ("Violet Turtle" and the like), it has an old or unconfigured build. Anything built without `.env.local` present falls back to demo mode silently.
12. **`web.output: "server"`** is left over from the Expo template and is what forces the Node pre-render; the app is native-only. Changing it to `"single"` would avoid that class of problem **[unverified]**, but was not done.
13. App Store/Play: nothing submitted. Advice given: TestFlight ($99/yr Apple Developer Program) first, Android as a direct APK until the app does real transfers; Play personal accounts need a 12-tester, 14-day closed test. Fees and rules came from search results, mostly third-party, and need confirming on official pages.
